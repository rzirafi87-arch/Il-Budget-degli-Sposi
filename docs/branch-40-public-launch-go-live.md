## Domain cutover

1. Add the owned domain to the Vercel project.
2. Add the exact DNS records displayed by Vercel at the authoritative DNS provider.
3. Decide whether apex or `www` is canonical and configure the other as a permanent redirect.
4. Wait for Vercel certificate status to become valid; test HTTPS and HSTS.
5. Set Production and Preview values as appropriate:
   - `SITE_URL=https://<canonical-domain>`
   - `NEXT_PUBLIC_SITE_URL=https://<canonical-domain>`
   - `NEXT_PUBLIC_ENVIRONMENT=production` (Production only)
6. Add `https://<canonical-domain>/auth/callback` and the recovery destination to Supabase Auth allowed redirect URLs.
7. Retest signup, confirmation, partner invitation, resend and password recovery.
8. Verify canonical metadata, OpenGraph, `robots.txt`, `sitemap.xml` and manifest on the canonical origin.

Without explicit values, server-rendered metadata uses Vercel's `VERCEL_PROJECT_PRODUCTION_URL`; the custom-domain switch requires configuration only.

## Production email / DNS

Use a dedicated sender such as `Il Budget degli Sposi <noreply@<verified-domain>>`; do not use `onboarding@resend.dev`.

1. Add the sending domain in Resend.
2. Publish the SPF and DKIM records exactly as generated by Resend.
3. Publish a DMARC record appropriate to the owner's policy after mailbox/reporting destinations are confirmed.
4. Wait for every required record to show verified.
5. Set `RESEND_API_KEY` and `RESEND_FROM` in Vercel Production.
6. Send controlled tests for signup confirmation, resend, recovery and partner invitation; verify From, Reply-To, links, SPF, DKIM and DMARC results.

DNS values must be copied from the live Resend verification screen; they must not be guessed.

## Legal completion checklist

The current policy pages are technical drafts, not legal approval. Before launch, provide and have counsel validate:

- controller/legal name, tax/VAT identification, registered address, PEC, privacy email and ordinary contact;
- representative and DPO details only if applicable;
- purposes, legal bases and retention periods for each data category;
- data-subject rights and complaint authority;
- age/eligibility rules, service conditions, liability, suspension and termination;
- processor/subprocessor list: Supabase, Vercel, Resend, optional Google Analytics and map/tile providers;
- international transfers and safeguards where applicable;
- cookie inventory and exact analytics configuration;
- effective date/version and process for policy changes.

## Backup and restore

Do not restore Production during drills.

1. Declare incident severity and identify the recovery point.
2. Freeze writes when continuing writes would increase loss or inconsistency.
3. Record current deployment, database version, migration list and row-count baseline.
4. Confirm the latest hosted backup and PITR window in Supabase.
5. Restore into an isolated recovery project.
6. Apply/compare repository migrations and generated types.
7. Validate RLS and advisors, couple access, event ownership, `expenses.event_id`, deletion requests and rate-limit objects.
8. Run authenticated and public smoke tests against the isolated environment.
9. Obtain an explicit promotion decision; never overwrite Production as a diagnostic step.
10. Verify Production after recovery and write a post-mortem with timeline, impact, root cause and prevention.

Record plan name, backup frequency, retention, PITR availability and the timestamp/result of the first recovery drill before public launch.

## Account deletion operations

Only an authorized operator may process rows with `status='pending'` and `scheduled_for <= now()`.

1. Identify the request by immutable user ID; do not trust an emailed identifier alone.
2. Confirm status is pending, the seven-day window elapsed and no cancellation exists.
3. Re-authenticate the operator and record ticket ID, operator, timestamp and row-count plan without copying user content into logs.
4. Enumerate user-global data and every owned/shared event.
5. For a shared event, verify the remaining partner through authenticated identity and normalized `bride_email` / `groom_email`; transfer ownership before deleting the requester.
6. Delete only requester-owned user-global data. Preserve event-scoped data required by the remaining partner.
7. Revoke sessions, then delete the Auth user last.
8. Mark the request completed only after verification. On partial failure, stop, retain the audit ticket and resume idempotently.
9. Verify the former user cannot authenticate and the partner still accesses the shared event.
10. Keep operational audit metadata only for the approved retention period; never log tokens, passwords or content.

No real account is used in tests and no automatic destructive job is enabled.

## Incident response

| Severity | Example | Response |
| --- | --- | --- |
| SEV-1 | Data exposure, destructive corruption, auth-wide outage | Freeze risky actions, preserve evidence, rollback safe application changes, isolate restore, notify owners immediately. |
| SEV-2 | Major module or email/auth degradation | Triage Vercel and Supabase logs, compare latest deploy, rollback if application-caused, validate RLS and recovery. |
| SEV-3 | Limited route or UX defect | Record, reproduce in Preview, fix through normal PR gates. |

For every incident: check 4xx/5xx, auth, RLS/advisors, database health, rate limits and Vercel runtime errors; recover with the smallest reversible action and write a post-mortem.

## CSP report-only inventory

Do not enable a restrictive CSP without runtime observation. Expected sources include:

- `'self'`, Next.js inline/bootstrap scripts and application images/fonts;
- the configured Supabase HTTPS and WSS project origins;
- map tiles/images used by the current Leaflet provider;
- Google Analytics / Tag Manager only after consent;
- Vercel platform assets where observed.

Introduce CSP as Report-Only in a later, dedicated hardening change after collecting violations on Preview.

## Final go-live sequence

1. Complete domain, email DNS, legal and backup/PITR external prerequisites.
2. Run repository quality gates and Database Rebuild.
3. Validate Preview routes, auth flows, consent, PWA and runtime logs.
4. Merge only with green GitHub CI, Database Rebuild and Vercel Preview.
5. Wait for Production `READY`; test public/private routes and critical APIs.
6. Review Production runtime errors and Supabase advisors.
7. Record the release commit, deployment ID, smoke evidence and rollback target.
